# Agent 工作流与提示词约定

## 目标和边界

工作流面向“AI 操作 Blender 完成场景，再导出为纯前端静态网页”。Coding agent 承担分析、文档、建模脚本、页面、检查和修复；用户在实现前确认规格。可重复脚本和 CI 负责硬门禁。规格确认后，全部门禁通过即可自动提交并 push，由仓库现有流程发布。

~~~mermaid
flowchart TD
    A[原始 Idea] --> B[Idea 简报与需求]
    B --> C[SceneSpec 与素材计划]
    C --> D{用户确认规格}
    D -- 修改 --> B
    D -- 确认 --> E[Agent 实现 Blender 场景和静态页面]
    E --> F[Blender / 素材 / 构建 / 浏览器检查]
    F --> G{检查和视觉自检通过}
    G -- 未通过且少于三轮 --> H[读取失败证据并最小修复]
    H --> F
    G -- 三轮后仍失败 --> I[停止并汇报，不发布]
    G -- 通过 --> J[提交并 push master]
    J --> K[仓库 CI 与共享站点部署]
~~~

## 阶段产物和通过条件

| 阶段 | 主要产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| Idea 澄清 | idea-brief.md | 目标用户、主要场景、核心操作和成功体验清楚 |
| 需求细化 | requirements.md | 每项需求能通过可观察行为或数值验收 |
| 场景设计 | scene-spec.md、scene-contract.json、assets/manifest.json | 尺度、构图、对象层级、交互、设备和预算已确定 |
| 人工确认 | 用户对上述规格的确认 | 用户确认后才能开始建模和网页实现 |
| 实现 | 可重跑的 Blender Python、.blend、GLB、静态网页 | 页面加载本地模型，有加载、成功、失败状态 |
| 质量检查 | 命令结果、Blender 渲染与浏览器预览 | 所有硬检查通过，Agent 对照 SceneSpec 完成视觉自检 |
| 发布 | 相关文件的 commit 和 master push | 推送触发现有 Actions；CI 成功后部署共享站点 |

规格发生会改变主体、相机目标、交互或预算的变更时，先更新文档并重新确认。实现阶段不得通过删除断言、降低质量预算或忽略错误来制造“通过”。

## SceneSpec 怎么写

把“做得好看”改写成能决定建模和检查行为的描述。每项重要视觉描述应对应对象、颜色/材质、空间关系、相机位置或可验收结果。

| 不够具体 | 建议写法 |
| --- | --- |
| 模型要精致 | 指明主体由哪些部件组成，哪些边缘要倒角，哪些部件允许简化 |
| 画面有氛围 | 说明背景色、主光方向、阴影软硬、色温和相机景别 |
| 可以交互 | 明确拖动、缩放、点击分别作用于哪个对象，以及重置行为 |
| 要流畅 | 明确目标设备、最大三角面数、纹理最长边、GLB 体积预算 |
| 用网上素材 | 说明所需资产类别、可接受许可和署名；来源不明时用程序化替代 |

第一版网页模板预算为 250,000 三角面、20 MiB GLB、2,048 像素纹理边长和 256 KiB JavaScript gzip 总体积。它们是模板默认值，须在该 Idea 的规格确认时显式展示；需要更高预算时由用户确认并同步更新 SceneSpec 和 scene-contract.json。

## 可复用提示词

### 1. Idea 到规格

~~~text
请只做需求细化，暂不操作 Blender 或编写网页。
阅读原始 Idea 后，填写 idea-brief.md、requirements.md、scene-spec.md 与素材清单。
把模糊描述转换成对象层级、尺度、相机/构图、材质/灯光、网页交互、目标设备和性能预算。
列出未确定的高影响假设，并为每项需求给出可以观察或脚本验证的验收条件。
不要虚构素材许可；无法确认的来源标记为阻塞项。
展示规格摘要和需要我确认的数值，等待我确认后再开始实现。
~~~

### 2. 确认后实现

~~~text
严格按已确认的 requirements.md、scene-spec.md 和 scene-contract.json 实现。
先生成可检查的灰盒与相机预览，再逐步增加材质和细节；保留可重复运行的 Blender Python。
网页只加载项目内的 GLB 和静态资源，不调用认证 API 或外部模型 CDN。
遇到规格冲突或素材许可问题时停止受影响的工作并说明，不自行改需求。
~~~

### 3. 检查失败后修复

~~~text
先读取失败命令、检查报告、Blender 渲染和浏览器截图。
定位根因后做最小修复，保留规格与门禁；修复后重跑受影响检查和完整发布门禁。
不得放宽预算、删除测试或把错误状态伪装成成功状态。
每轮记录问题、原因和修复；累计三轮仍未通过就停止并汇报。
~~~

## 素材接入和许可

- 优先搜索已配置的免密 3D Assets MCP、BlenderKit/Blendkit 和本机程序化建模能力。
- 外部素材下载后，将来源 URL、作者、资源名或 ID、获取日期、许可、署名要求、再分发许可和本地文件位置写入清单。
- 页面是公开静态托管：必须确认许可允许复制、缓存和再分发。未知许可和限制冲突都不能发布。
- 不把 MCP 配置、API key、Cookie、插件登录数据写入项目、场景文件或网页构建目录。Sketchfab OAuth/API 不属于当前接入范围。

## 门禁与失败处理

| 门禁 | 自动验证内容 | 失败时 |
| --- | --- | --- |
| 素材检查 | 清单结构、许可状态、署名字段、来源 URL、路径存在且未逃出项目目录 | 获取可再分发素材或改为原创/程序化资产 |
| Blender 检查 | 活动相机、非空网格、关键对象、变换数值、贴图引用、三角面/贴图/体积预算、GLB v2 头部 | 修复场景/导出，不更改批准预算 |
| 网页构建 | TypeScript 和 Vite 构建、JavaScript gzip 总体积、GLB 文件结构、路径与相对部署 base | 修复加载资源或构建路径 |
| 浏览器检查 | 静态页面打开、无页面异常、GLB 成功加载、画布和状态可见 | 检查浏览器日志与模型错误，再修复 |
| Agent 视觉自检 | 渲染和网页截图与已确认的构图、比例、交互目标一致 | 记录视觉差异并修复；最多三轮 |

JavaScript 预算按构建后所有 JS 文件的 gzip 字节数求和。模板当前实测约 159 KiB，默认 256 KiB 为项目 UI 留出扩展空间；预算针对压缩传输体积，不以 Vite 的未压缩 chunk 警告代替门禁。

Blender 检查由本机脚本执行，因为 GitHub Actions 不安装 Blender。静态资产和浏览器检查由成品应用的 test:ci 在本机/CI 运行。门禁三轮后仍失败、不具备本机 Blender、或许可无法查清时，不 push；报告阻塞细节供用户决定。

## 提交和发布

成品应用位于 apps/<slug>，应用自身提供 package.json、pnpm-lock.yaml、scripts/install.sh、build 和 test:ci，并登记 apps/catalog.json。Agent 只有在用户确认规格且本地发布门禁通过后才提交并 push master；仓库 Actions 再运行应用测试和共享站点构建，测试通过后发布 GitHub Pages/Cloudflare Pages。blender-lab 模板目录的改动只运行框架测试，不发布网页。
