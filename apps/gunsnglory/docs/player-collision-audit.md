# 我方桥面与地图对象碰撞审计

## 范围与结论

对照对象是 Guns’n’Glory Android APK 1.8.6 的静态 DEX/资源，与网页 `GameSession` 和关卡 TDM 数据。APK 未在本次检查中运行；结论来自具体方法、对象构造参数、TDM 网格和 APK 资源字节。

APK 战役包含60个可玩关卡；本审计对应的早期实现批次接入27张正式地图。当前集成分支已接入41张正式地图。共享测试 `player-collision.test.ts` 已逐图检查41张地图的静态 TDM 对象框，`player-unit-anchor.test.ts` 已逐图检查41张地图的初始单位/唤醒锚点和 raw36 墙边移动探针；新增 `all-maps-player-bridge.test.ts` 对41张地图中实际渲染且两侧为 raw32/36 阻挡格的每个连通桥段运行短 `GameSession`，检查沿桥通行和两侧边界停靠。**这不等于所有地图特有动态对象均已做逐图会话验证，也不等于完成了原版运行画面逐图比对。**尚未接入的 Level 42–60 不在本次矩阵范围，详见[地图覆盖矩阵](map-coverage-matrix.md)。

**桥面贴图和绘制尺寸没有发现与 APK 的差异。**此前“走到桥下/峡谷壁”的问题应拆成两类：raw `36` 悬崖壁曾漏进网页阻挡码，已在前一修复批次补齐；此外，网页的完整对象碰撞确实缺失/错位，单位能穿过睡眠角色和部分静态设施。本批修复对象碰撞，不平移桥图、不缩窄原版道路、不改玩家碰撞框。

## 桥面的原版画面与行走规则

### 绘制对照

| 原始 TDM 格 | APK 街道码 | APK 资源 | 单格绘制尺寸 | 锚点/位置 |
| ---: | ---: | --- | ---: | --- |
| `80` | `64` | `tiles_bridge_hori.png`，48×32 px | 1.5×1 格 | 水平居中于该格，竖向覆盖该格 |
| `88` | `76` | `tiles_bridge_verti.png`，32×48 px | 1×1.5 格 | 横向覆盖该格，纵向居中于该格 |

APK `BackgroundMap.createStreetLayerMap()` 负责 raw TDM 到街道码的映射；`GunsAndGloryThread.drawStreetLayer()` 依据位图像素尺寸乘 `tileSizeFactor` 计算目标矩形，并将另一轴固定为一个 `realTilesize`。网页对应的道路绘制命令使用相同尺寸与中心位置；项目内两张 PNG 与 APK 中相应 drawable 的字节校验一致。桥面绘制是道路覆盖层，不是底图，也不是实体碰撞框。

Cow Gulch raw `80` 位于 `(12,9)`，横桥贴图范围为 `x=[11.75,13.25]`、`y=[9,10]`。raw `88` 的竖桥贴图范围为 `x=[x,x+1]`、`y=[y−0.25,y+1.25]`。相邻桥段的半格重叠是位图尺寸导致的原版绘制结果，不应把绘图范围直接当成可行走矩形。

### 玩家碰撞框

APK `GameObjectUnit` 构造时把 TDM 格中心 `(x+0.5,y+0.5)` 的 Y 加 `1920`，形成脚底锚点 `(x+0.5,y+0.75)` 格。`createCollisionObject()` 再以该位置创建 `5068×4608` fine-unit 碰撞框：

```text
每格 7680 fine units
左边 = fineX − 2534       右边 = fineX + 2534
上边 = fineY − 5376       下边 = fineY − 768
```

`BackgroundMap.isReachableXGround()` / `isReachableYGround()` 分别在候选移动位置检查该框的四个角。底图格被标为阻挡时，只有该角所在格的街道层非空才能放行。Cow Gulch 桥格上、下方 raw `32` 都阻挡，因此横桥行走锚点约束为 `9.7 ≤ fineY/7680 < 10.1`：上边界由碰撞框上角越入第8行决定，下边界由下角越入第10行决定。框的下边比可见脚底锚点高 `0.1` 格，所以贴图脚底可比碰撞边缘多出最多约 `0.1` 格；这是 APK 碰撞框与精灵脚底锚点的关系，不应通过整体改小桥或移动路线来掩盖。

**边界结论：**如果脚底仅略过桥图边缘，先核对上述锚点和框；如果单位进入 raw `36` 悬崖墙、穿过睡眠角色或穿过建筑，则是地形/对象阻挡问题，不能归因于桥面 PNG 尺寸。

## APK 静态对象碰撞框

以下矩形是 APK 碰撞框相对于 TDM 格左上角的坐标，单位均为 fine units；由 `GameObjectManager.createGameObjectsFromBasicMap()` 的对象分类、构造器锚点和 `CollisionManager.createCollisionObject()` 合并换算。

| TDM 标记 | 原版对象 | 相对格左上角 `(x,y,w,h)` | 说明 |
| --- | --- | --- | --- |
| `68,69,71–76,79,117,126` | 普通装饰、树、桩、灌木、风车、水塔、小 tipi、水边岩石 | `(1920,2612,3840,2534)` | 绘制图可能大于底部碰撞区；按原版小框阻挡 |
| `70` | rocks B | `(1306,1920,5068,3840)` | 特殊大框 |
| `77` | bones | `(0,−5760,7680,11520)` | 高物体向上覆盖两格 |
| `86,87,94,95` | 铁路挡车器 | `(0,0,7680,7680)` | 占一整格 |
| `116` | shack | `(−7680,2612,15360,3840)` | 宽两格，锚点横移半格 |
| `112,150` | saloon、已解锁 casino | `(−2496,−4224,14592,6144)` | casino 只在原版创建它时阻挡 |
| `113` | fort | `(−5568,−5760,18048,7680)` | 宽大建筑 |
| `114` | tipi | `(−5184,−2304,10368,4224)` | 建筑碰撞框 |
| `102,110` | dynamite trigger/box | 单位框 `(−2534,−5376,5068,4608)` | 仅在对应炸药对象已解锁并创建时加入 |

`GameObjectUnit.setUnitActivity(4)` 只修改状态、朝向和贴图，没有注销碰撞框。活动和睡眠单位均由 `GameObjectUnit.createCollisionObject()` 登记到 `cmUnits`。`GunsAndGloryThread.onLoadGame()` 创建 `cmUnits(bgm, true, false)`：检查底图、且不忽略同组对象碰撞。

移动对象时，`CollisionManager.testCollision()` 实际调用 `boxCheckX()` 与 `boxCheckY()`：分别检查移动框边沿在本帧位移后是否穿越障碍边缘，并要求另一轴区间重叠；端点按源码的 `<=`/`>=` 语义计入。它不是对候选位置简单做 AABB 重叠，也不是只检查四角。独立的 `boxCheck()` 是另一段辅助判定，不能代替移动调用链。`GameObjectSpawnLocation.update()` 在新增单位时调用 `testBasicCollision()`，即零位移的碰撞检查；因此建筑生成锚点可以和建筑碰撞框局部重叠，随后单位依据真实移动方向离开建筑。

动态对象有两个特殊边界：奖励 `GameObjectCollectable` 使用可收集碰撞对象，碰到后发奖并从碰撞集合移除；DynamiteBox 爆炸时 `detonate()` 仅把 `mActive` 设为 false，`draw()` 因而暂时不绘制，但没有注销碰撞框，`respawn()` 后重新显示。网页不能把奖励箱当永久墙，也不能因炸药箱暂时不可见就擅自移除原版阻挡。

这些代码没有创建普通静态对象碰撞框的标记包括 `78`、道路/桥面图层码、`115`、`118`、`119`。列车/蒸汽机、活动/可招募单位、炸药对象应按 APK 对象类型作为动态单位处理，不能把它们重复解释成静态装饰。

## 网页实现差异与失败原因

| 项目 | APK 基线 | 先前网页实现 | 表现 |
| --- | --- | --- | --- |
| 桥面底图判断 | 单位框四角分别检查背景格和道路覆盖格 | 已能用 raw `80/88` 道路层放行；前一批补齐 raw `36` 阻挡 | raw36 修复前可穿入可见悬崖墙；桥贴图尺寸本身未发现差异 |
| 静态对象 | TDM 建立 Decoration/SpawnLocation；每类在 `createCollisionObject()` 中生成不同框 | 只查 `MapDecoration.collisionBoxFine`，很多建筑没有字段；部分字段的 y 偏移和 Fort 等大物体框不符 | saloon 等对象可穿过；错框使部分障碍提前、偏侧或滞后阻挡 |
| 我方单位 | 活动、沉睡和新建单位都在 `cmUnits` | `mapBlocksUnit()` 没有接收 `units` 列表 | 睡眠槽、活动队友可被穿过 |
| 接触语义 | `boxCheckX/Y` 检查当前碰撞框沿本帧位移穿越障碍边沿；另一轴区间重叠时阻挡 | 先前静态对象用严格 AABB 重叠，没有区分“沿边穿越”与“出生时已经重叠” | 桥/墙边界与建筑重叠出生状态不匹配；炮池单位可能被自身建筑挡住 |
| 生成点 | `GameObjectSpawnLocation.update()` 用 `testBasicCollision()` 做零位移检查，按原版 spawn anchor 生成 | 生成处另用严格矩形重叠 | Fort 炮位上的 Cannon 会被错误判为生成受阻，或被困在自身建筑边缘 |
| 特殊移动框 | 每个移动对象使用自己的 `CollisionObject`，例如 Steamer 船体框 | 水面对象需要自定义框，但地图对象检查曾忽略该移动框 | 水面碰撞回归会改变 Steamer/水岩交互 |
| 自定义静态物体 | 原始 TDM 对象码决定 APK 对象类别；部分自定义物体位于普通地形 | TDM 网格和显式装饰框曾二选一 | 使用原始网格时仍要保留水岩等特殊装饰的显式框 |
| 回归测试 | 以 APK 参数为期望 | 旧静态装饰测试把待测 `collisionBoxFine` 自身当期望 | 测试能在坐标错误时通过，没覆盖睡眠单位和无显式框的建筑 |

修复实现以原始 TDM 网格作为正式关卡静态对象的几何来源；TDM 码没有 APK 静态框时，仍采用显式字段承载的特殊对象（例如水面岩石），无原始网格的手工场景也保留该 fallback。玩家、移动组、船体和单位池生成都使用对应移动对象框；对象移动检查复刻 APK 的 X/Y 边沿穿越规则，桥面地形仍使用四角采样。Fort 生成点保留零位移检查，单位锚点和贴图外框不混作碰撞框。

## 验收边界

- 静态 TDM 网格与原版对象码分类逐图比较，避免把未实例化的资源码当障碍；`player-collision.test.ts` 对41张正式地图的每个对象标记检查唯一 APK 碰撞框及非碰撞码排除。
- `all-maps-player-bridge.test.ts` 对41张正式地图中每个符合 TDM 两侧阻挡条件的已渲染桥段做短会话边界移动；其他对象类别由对应真实地图的短会话用例核验。桥面会话不等于 Android 原版运行画面对照。
- 地形与静态对象分别验证：地形使用 `BackgroundMap.isReachableX/Y` 四角采样；对象使用 `CollisionManager.testCollision → boxCheckX/Y` 的边沿穿越语义。不要用 AABB 重叠或对象角点代替源码调用链。
- 不把 sprite 外框、建筑绘制范围、桥面贴图范围当碰撞框；spawn 和移动也必须按不同 APK 调用点验证。
- 如果之后在同一桥面复现进入墙格，先记录原始位置与候选四角对应的背景码/街道码，再判断是否为碰撞代码回归；不得只凭屏幕相对贴图判断要改桥宽或单位锚点。
- 自动化会话可证明规则运行结果，不等价于原版 APK 运行观察。本批不启动 Android；若仍有静态代码无法判定的实际渲染差异，再对该具体差异做单点运行观察。
