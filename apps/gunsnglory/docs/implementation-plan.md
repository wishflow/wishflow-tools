# 实施计划

本文是 Guns’n’Glory 唯一活动进度与任务来源，只保留未完成工作。产品规则见[产品规格](spec.md)，模块边界见[架构](architecture.md)，存档边界见[存储契约](storage-contracts.md)，模拟与测试约束见[模拟与自动化契约](simulation-and-automation.md)。

每轮先核对当前代码、测试与提交，再细化后续步骤的范围和验收。每个切片先跑针对性测试并提交；步骤完成后更新本文，删除已完成项。整批结束再跑一次完整检查，不重复已通过的检查。

- 正式战役已完成 **3/60** 关：Cow Gulch、Apache Valley、Fort Kaboom。
- 当前工作在 `codex/gng-spawn-field-restore`；该分支包含 `gunsnglory` 集成分支，尚未集成到公开 `master`。公开版本为 `e922c3f`，本地代码不等于已发布版本。

- 全屏画面现按可用视口保持比例适配，窗口模式下 Usagi 位于游戏上层并可交互，全屏状态隐藏、退出后恢复。定向视口测试、5 项全屏 E2E 及本批完整 `test:ci` 均通过；内置浏览器拒绝网页的原生全屏请求，因此原生全屏覆盖屏幕这一项仍没有浏览器实测证据。后续一般保持窗口模式，不重复进入全屏；若专门回归全屏，再记录真实浏览器能力和结果。
- 发布比例基线为 5 次成功发布 / 27 个已验收实现切片（18.5%）；完成新的发布批次后再按规则更新计数。

## 下一步

### 1. Tech Town 参数证据闭环

- 对照已保存的 APK/REA Evidence 与现有 `GameDesignData`、`GameDesignWaves` 及 `SpawnPoolManager` 分析，确认八波每条请求向量的类型映射、敌方生成池动作、玩家单位池动作、间隔/延迟/倍率与字段消费者。
- 逐项核对 map04 十二个原始关卡参数在 DEX 中的读取位置、单位及实际作用。只把有明确消费者且影响正式关卡的字段列入实现；不影响网页核心或尚无消费者的字段记录为不使用/未知，不猜行为。
- 确认八段对白的原文、触发波次、说话者和肖像映射，并定位现有资源或现有窗口流程的复用入口。中文译文按语义补齐，不伪称为 APK 原文。
- 产出一份实现用的紧凑映射表，逐项标出 APK/REA 证据位置、网页目标文件和状态；静态材料足够时不启动 Android。若发现 REA 结果缺失，只调用对应只读静态工具，不重做已完成的地图或单位审计。
- **关闭条件：**每个将实现的字段和波次动作均有可追溯证据；明确哪些原始字段不适用或不确定；没有依赖手打完整关卡才能回答的问题。若有影响核心内容的未知项，先写出具体阻塞和所需工具/输入，再暂停依赖它的代码。

### 2. Tech Town 可玩内容接入

在证据闭环后，基于现有正式关卡、波次、单位池和对白接口创建 map04 内容；不改已验证的通用规则，除非针对性测试证明接口表达不了原版行为。

实施范围：

- 按 APK 顺序接入八波敌方请求、生成入口、时间间隔、延迟、生命/速度倍率和第 2 波池动作；单独验证 request type 映射，避免把 Wave Pool type 当作敌人类型。
- 接入玩家生成池与对应关卡动作，并核对实际地图生成点、单位解锁和可招募集合。玩家池与敌方波次池使用各自的数据结构，不混为一体。
- 按已映射字段设置正式开局经济、生命及其他实际生效参数；确保胜负与关卡完成只产生一次正式档案结算，解锁 map05。
- 接入八段双语波次对白、原版说话者/肖像、波次触发关系及正式资源预加载；常规检查静音，不播放音效。
- 将 Tech Town 注册为第 4 个正式战役关卡：map03 完成后可进入；未完成 map04 时 map05 保持锁定；完成 map04 后 map05 解锁。Gambler/Casino 等档案条件沿用现有同一进度快照。

验收：

- 自动化内容测试逐项比对 APK-derived 波次矩阵、池动作、玩家池、关卡参数、对白键/文本/肖像和解锁关系；预期值不得从被测内容本身动态生成。
- Game/Progress 会话测试覆盖从开局到波次推进、关键池动作、胜利/失败及唯一结算；不得要求人工通关，也不得以独立测试 fixture 代替正式 map04 数据。
- 窗口模式、静音；内置浏览器只检查选关、进入 Tech Town、八波内容已挂接、一个代表性操作和退出/结算入口。完整规则由自动化检查覆盖。
- 两个步骤各自运行针对性检查并提交；整个 Tech Town 功能批次完成后运行一次 `pnpm run test:ci` 和适用共享检查，再按正式功能批次规则集成/发布。

### 3. 后续战役

map04 验收后逐关处理 New Mexico map05–10，再处理 Mississippi map14–23、Oregon map24–33、Dakota map34–43、Nevada map44–53、Alaska map54–63。每关先复核 APK 与现有框架，只实现该关实际需要的数据或新机制；APK 地图文件 11–13 不计入 60 关战役。首次出现的新敌人、建筑、交通工具或规则只在真实使用场景验证。

## 证据与发布门槛

- 每个新增规则或参数都能追溯到 APK 资源、REA 结果、DEX 位置或明确标记的运行观察；JADX Java 伪代码不是原始源码。曾发现 `GameObjectManager.createGameObjectsFromBasicMap()` 的 Java `switch` 输出有控制流错误，码位判断以 DEX smali 为准。
- 只有具体行为无法由静态证据回答时，才执行一次最小 Android 观察；记录问题、设备状态、判定标准和结果。不重复看启动页，不模拟完整战役。
- 发布按应用规则执行：每个切片先定向验证并提交；批次全套检查通过后以一个 squash commit 集成。普通发布比例目标不高于 20%，核心缺陷修复按实际情况记录；公开发布核对 CI、来源 SHA 与内置浏览器结果。文档整理不计实现切片、不单独发布。
