## M36：Ghost Town 内容接入

依赖：M35 Dakota 内容与共享地图/碰撞/路线框架。接入数据仅以本关静态审计和 APK 原始资源为准；旧摘要只能作检索线索。实现过程中如发现差异，先回原始 TDM/Smali/resource consumer 核实，再更新审计与本计划。

### G3：关卡规则与内容数据

各步骤使用 `ghost-town-static-audit.md` 的独立 APK 派生表做期望值；波次请求向量按“剩余数量”验证，不把它们误读为确定的逐个敌人顺序。池计时目前沿用网页现有15秒默认值，静态报告尚未证明它是 APK 针对本关的专属间隔，测试与交付说明必须保留这一限制。

#### G3-A：关卡参数与奖励箱

- **范围：**新增 Ghost Town 的12项 index34 参数和关卡规则绑定：初始现金/生命、箱子总量/间隔/场上上限、升级上限、awesome-message 字段、三档敌人 HP 百分比、Gambler 时间字段。没有 Gambler/Casino marker，不创建赌徒或赌场。
- **验收：**参数值逐项为 `[300,25,999,25000,3,30000,5,15,56,75,95,118000]`，映射含义与静态审计及现有 `ScenarioContent` 消费者一致；仅把已有运行契约支持的值接入行为，awesome-message 与 Gambler 字段不擅自推导额外效果。
- **验证：**新增独立期望的参数测试；短 `GameSession` 核对初始现金/生命和难度倍率、奖励箱上限/计时及升级上限。类型检查通过后更新计划并本地提交。

#### G3-B：九波和十九条敌人请求

- **范围：**按 APK 源顺序接入9个 wave header、19个 spawn pool 请求及其开始延时、HP/速度倍率、action、间隔、8个普通槽、Boss/Doc 槽。action 映射只引用已验证的四个 `dakota05SpawnPointIdByActionId`。
- **验收：**每一波每个字段及10槽请求数组与独立 APK 期望完全相等；Boss 位于网页第9槽（index 8），Doc 位于第10槽且本关为0；不改变共享随机选型或把请求向量当成出敌顺序。
- **验证：**独立 fixture 覆盖完整9波/19请求；短会话验证首波延迟、首个实际出生事件来源 action 和末波 Boss 事件，使用来源事件 ID 判断出生口，不用首帧坐标推断。不得推进完整战役。

#### G3-C：玩家单位池与建筑生成

## 批次执行规则

- 每个实现切片先运行针对性验证、更新本计划并本地提交；一组步骤完成后重新核对未完成项和依赖。
- 整批结束时运行完整应用检查和适用共享检查一次。失败留在当前批次修复，再重跑失败项及最终完整检查。
- APK数据期望必须独立于生产数据；路线、绘制、碰撞、单位、规则、内容入口分别验证。不能用DOM可见、fixture自洽或单张预览图证明完整行为。
- 发布是完整功能批次的决定，不按文档或单个实现切片发布。部署与内置浏览器门槛未通过时，批次保持未完成。
